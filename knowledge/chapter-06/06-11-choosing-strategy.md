# Выбор стратегии управления состоянием

## Введение

Один из самых сложных вопросов при разработке Flutter-приложений — выбор стратегии управления состоянием. Нет «лучшего» решения для всех случаев: каждый подход имеет свои преимущества и недостатки.

> **Ключевая идея:** Выбор стратегии зависит от размера проекта, опыта команды и требований приложения.

## Рекомендации по размеру проекта

### Маленькие проекты (1-10 экранов)

**Рекомендация:** `setState()` + `Provider`

```dart
// Пример: Простое приложение-счётчик
void main() {
  runApp(const MyApp());
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: CounterPage(),
    );
  }
}

class CounterPage extends StatefulWidget {
  const CounterPage({super.key});

  @override
  State<CounterPage> createState() => _CounterPageState();
}

class _CounterPageState extends State<CounterPage> {
  int _count = 0;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Center(child: Text('Счётчик: $_count')),
      floatingActionButton: FloatingActionButton(
        onPressed: () => setState(() => _count++),
        child: const Icon(Icons.add),
      ),
    );
  }
}
```

### Средние проекты (10-50 экранов)

**Рекомендация:** `Provider` или `Riverpod`

```dart
// Пример: Приложение с несколькими экранами
void main() {
  runApp(
    MultiProvider(
      providers: [
        ChangeNotifierProvider(create: (_) => CounterModel()),
        ChangeNotifierProvider(create: (_) => UserModel()),
      ],
      child: const MyApp(),
    ),
  );
}

class MyApp extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: HomePage(),
    );
  }
}

class HomePage extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Center(
        child: Consumer<CounterModel>(
          builder: (context, counter, _) {
            return Text('Счётчик: ${counter.count}');
          },
        ),
      ),
    );
  }
}
```

### Большие проекты (50+ экранов)

**Рекомендация:** `BLoC` или `Riverpod`

```dart
// Пример: BLoC для большого проекта
void main() {
  runApp(
    MultiBlocProvider(
      providers: [
        BlocProvider(create: (_) => CounterBloc()),
        BlocProvider(create: (_) => AuthBloc()),
        BlocProvider(create: (_) => TodoBloc()),
      ],
      child: const MyApp(),
    ),
  );
}

class MyApp extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: BlocBuilder<AuthBloc, AuthState>(
        builder: (context, state) {
          if (state is Authenticated) {
            return HomePage();
          }
          return LoginPage();
        },
      ),
    );
  }
}
```

## Рекомендации по типу приложения

### CRUD-приложение

```
Рекомендация: Provider или Riverpod

Причина: Простое состояние, не нужна сложная архитектура
```

### Приложение с реальным временем (чаты, уведомления)

```
Рекомендация: BLoC или Riverpod

Причина: Хорошая обработка потоков данных
```

### Игра или анимационное приложение

```
Рекомендация: setState() или MobX

Причина: Высокая производительность, минимальные задержки
```

### Enterprise-приложение

```
Рекомендация: BLoC или Redux

Причина: Строгая архитектура, легко тестировать
```

## Практические примеры выбора

### Пример 1: Приложение-список покупок

```
Характеристики:
- 5 экранов
- Простое CRUD
- Нет реального времени

Выбор: Provider

Причина: Простое решение для среднего проекта
```

### Пример 2: Социальная сеть

```
Характеристики:
- 30+ экранов
- Реальное время (чат, уведомления)
- Сложная бизнес-логика

Выбор: BLoC

Причина: Чёткое разделение ответственности, хорошая тестируемость
```

### Пример 3: Приложение для заметок

```
Характеристики:
- 10 экранов
- Локальное хранение данных
- Простая бизнес-логика

Выбор: Riverpod

Причина: Современное решение, хорошая производительность
```

## Best Practices

### ✅ Делайте

- Начинайте с простого решения
- Документируйте выбор архитектуры
- Используйте единую стратегию в проекте
- Тестируйте бизнес-логику отдельно от UI
- Рефакторите при необходимости

### ❌ Не делайте

- Не выбирайте архитектуру «на вырост»
- Не смешивайте несколько стратегий
- Не усложняйте без необходимости
- Не игнорируйте производительность

## Заключение

Выбор стратегии управления состоянием — это компромисс между простотой и масштабируемостью. Не существует идеального решения: каждый подход имеет свои преимущества и недостатки.

> **Правило:** Начните с простого (setState → Provider) и усложняйте только при необходимости. Лучше иметь простое решение, которое работает, чем сложное, которое не нужно.
